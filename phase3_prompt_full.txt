# 1. ESTABLISH THE CORRECT DEFAULT CURRENCY WORKSPACE

The current default currency workspace is wrong.

At the moment, fresh/opened currency workspaces can contain currencies such as:

- OMR
- TZS
- KMF
- KES

Those currencies were being used during testing.

They were **NOT intended to become the permanent/default startup currency configuration.**

They were test currencies.

## Correct default startup workspace

For a fresh/default OmniCalc currency workspace, the initial five currencies should be:

### Position 1
**USD — United States Dollar**

### Position 2
**EUR — Euro**

### Position 3
**KES — Kenyan Shilling**

### Position 4
**TZS — Tanzanian Shilling**

### Position 5
**KMF — Comorian Franc**

This is the intended default ordering.

The user must then be able to customize this workspace.

For example:

USD  
EUR  
KES  
TZS  
KMF

can become:

KES  
USD  
KMF  
EUR  
TZS

through normal drag-and-drop.

The default ordering is therefore only the **initial state**, not a permanent forced ordering.

# 2. VERY IMPORTANT: SEPARATE DEFAULTS FROM USER WORKSPACE STATE

This is the most important architectural requirement of this phase.

Do not allow the application to repeatedly inject the default currencies into an existing user workspace.

There must be a clear distinction between:

### A. Default workspace configuration

Used when the application has never initialized the currency workspace.

Default:

1. USD
2. EUR
3. KES
4. TZS
5. KMF

### B. User workspace configuration

Once the user has:

- removed a currency
- added a currency
- reordered a currency
- changed the active input currency

the workspace belongs to the user.

The application must respect that state.

## Example

User starts with:

USD  
EUR  
KES  
TZS  
KMF

User removes:

EUR  
TZS  
KMF

Workspace becomes:

USD  
KES

The application must NOT subsequently decide:

"Only two currencies remain, therefore I should add TZS or KMF or OMR."

It must remain:

USD  
KES

until the user explicitly adds another currency.

# 3. CRITICAL BUG: CURRENCIES ARE BEING REINSERTED DURING REORDERING

There is currently a serious state-management problem.

When only two currencies remain, reordering them can cause previously removed/default currencies to mysteriously reappear.

For example:

Current workspace:

1. TZS
2. KMF

User drags:

TZS downward

to produce:

1. KMF
2. TZS

Instead of simply changing the order, another currency such as KES may suddenly appear.

Another example:

Current workspace:

1. OMR
2. KES

User drags OMR below KES.

Instead of simply becoming:

1. KES
2. OMR

another default currency such as TZS may appear.

This is unacceptable.

## Required invariant

### DRAGGING MUST NEVER CHANGE MEMBERSHIP.

A reorder operation may change:

- position
- orderIndex

It must NEVER change:

- which currencies exist in the workspace
- the number of currencies
- the user's selected currencies

unless the user explicitly adds or removes a currency.

Formally:

If the workspace before dragging contains:

`[A, B]`

then after dragging it must contain exactly:

`[B, A]`

and absolutely nothing else.

Not:

`[B, A, C]`

Not:

`[C, B, A]`

Not:

`[B, A, defaultCurrency]`

Only the order may change.

# 4. MINIMUM TWO-CURRENCY RULE

The existing behavior that prevents the user from removing the final currencies is good.

Maintain the rule that the currency workspace must contain at least two currencies.

Therefore:

If there are two currencies:

[A, B]

the user can:

- reorder A/B
- edit them
- replace one through the normal currency selection workflow

but cannot remove both.

If the user taps X on A:

workspace becomes:

[B, another existing currency]

only if another currency already exists.

Do NOT automatically insert a default currency merely because the workspace reaches two currencies.

The minimum-two rule is a **minimum membership constraint**, not a **default-currency injection trigger**.

This distinction is critical.

# 12. ORDERING DATA MODEL

Review the current `orderIndex` architecture.

The invariant should be:

For workspace:

[A, B, C, D]

the persisted order should be:

A → 0  
B → 1  
C → 2  
D → 3

After moving D to the top:

D → 0  
A → 1  
B → 2  
C → 3

There must be no duplicate order indices.

There must be no gaps unless the architecture intentionally normalizes them.

After every successful reorder:

1. UI state changes immediately.
2. New order is persisted.
3. Room contains the same membership.
4. Room contains the same order.
5. Restart restores exactly that order.
